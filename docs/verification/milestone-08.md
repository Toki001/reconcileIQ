## Audit and implementation plan

Existing behavior: API request IDs and safe problem responses, database-backed job/attempt/outbox/failure histories, supervised Celery recovery, strict PDF/OCR child, immutable candidates/reconciliation and bounded provider usage already exist. There is no implemented OTel/Prometheus/Tempo/Grafana/k6 stack. Existing smoke timings are synthetic development probes, not distributed trace or performance certification. Reuse all business transactions and isolation boundaries.

1. Add a small shared telemetry package with official stable OTel SDK/OTLP libraries and compatible official instrumentations. Enforce allowlists before span attributes/events enter SDK storage; disable exception payloads and automatic metric labels. Use explicit bounded domain metrics and no-op defaults. Collector failure cannot abort business operations.
2. Propagate validated W3C traceparent through new durable outbox payloads and RabbitMQ headers, preserving correlation over dispatch/retry/recovery. Delayed attempts use links where appropriate. Instrument HTTP/GraphQL/SQL, publication/tasks/storage, parser/OCR, provider abstraction, matching and human review without changing monetary decisions. Keep pure reconciliation dependency-free.
3. Add an optional local observability overlay: pinned collector, Prometheus, Tempo and provisioned Grafana; internal endpoints/loopback UI, bounded queues/retention/resources, five real-metric dashboards and runbook-linked alerts.
4. Build a separate benchmark project/database/broker/MinIO with independent credentials, ports and volumes. All admissions, failures, restarts, load and service integrations target that project. Capture retained-row hashes read-only before/after; never benchmark or fault the retained stack.
5. Measure a bounded API baseline, sustained >=2 submissions/minute, burst/admission backpressure, worker replacement, RabbitMQ/MinIO recovery and observability outages. Record actual k6 summaries, database job/attempt/effect consistency, resource samples and complete exported trace relationships. Digital/OCR/mock/live AI measurements remain explicitly distinct.
6. Preserve full regression/coverage/contracts/build checks, test redaction/propagation/export failure/configuration, document actual evidence and limitations, then commit the requested milestone only.

## Commit-counter defect and fix

The original post-flush observer filtered jobs solely using `state.history.has_changes()`. SQLAlchemy populates a Python column default during INSERT flush without recording an explicit attribute change. A newly inserted job using the default `pending_dispatch` state therefore emitted no post-commit observation. The regression exposed this as absent metric data, not a failed financial commit.

The listener now includes new Job instances as well as explicit state changes. It buffers the final state per job per transaction. Savepoint commits merge into the parent buffer; only the outer durable commit emits counters. Nested rollback discards only that savepoint, outer rollback/failed flush/closed transactions discard uncommitted observations. Multiple flushes coalesce, and an unchanged terminal state on duplicate processing emits no additional terminal count. Actual failure states are counted as failed, never successful. Listener exceptions are contained. No listener invokes commit, rollback, flush, publication, financial validation or a business-state mutation.

Targeted tests verify default inserts, rollback, nested commit followed by outer rollback, nested rollback with outer commit, final-state coalescing, failed flush after a tentative success, repeated flush/no-op delivery, observer exceptions, and synthetic provider duplicate delivery. The initial counter failure is fixed: **26 passed / 1 expected PostgreSQL skip**, followed by an additional GraphQL error-classification test. A focused subsequent run passed **77 / 2 expected PostgreSQL skips** across telemetry, contracts, foundation and authorization cases. The full offline suite and focused branch gate passed; the final PostgreSQL telemetry run passes all 32 cases. Results are recorded below.

Actual OTLP -> Collector -> Prometheus verification uses a disposable PostgreSQL schema and an isolated service-instance label. It observes exactly one pending, one failed and one succeeded transition, plus one failed/one successful completion. An outer rollback after a committed savepoint, ordinary rollback, failed flush and unchanged duplicate update add no observations. The test schema is removed; no retained records are used.

These are operational, best-effort post-commit observations. A process crash after database commit but before export may lose metrics; counters are not an exactly-once financial ledger. Durable database state, immutable evidence and append-only audits remain authoritative. Queue-wait/terminal histograms use committed database timestamps, not human-review time.
