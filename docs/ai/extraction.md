# Structured extraction and review

Digital text remains the primary source. Upload completion verifies SHA-256, PDF signature, MIME and size, seals an independent MinIO object, and admits the existing durable Celery job. Successful text is immutable **untrusted** `digital-text-v1` evidence. It does not establish financial values.

Structured extraction is a separate, explicit `POST /v1/invoices/{id}/structured-extractions` with optimistic version, idempotency key and synthetic authorization. It requires a fresh verified free-project status and a digest in the repository's synthetic fixture manifests. The worker independently re-verifies project eligibility and acquires a shared PostgreSQL request/concurrency budget. It sends bounded page text only, never paths, objects, environment values or credentials. The official SDK has one attempt per worker attempt, no tools, no automatic function calls and no fallback model.

`InvoiceCandidate` strictly validates header and line evidence. Money is bounded integer minor units for USD/EUR/PHP/JPY/KWD; quantities and tax rates are decimal strings. Missing values require null/empty evidence; inferred values cannot satisfy matching requirements. Observed values require a real page, an exact quote from that page, and a supported value in the quote. Dates require valid ISO dates. This conservative validation does not prove semantic truth: an unrelated matching number in a quote can still be misleading. Human inspection remains required.

Each accepted candidate creates a sealed, append-only extraction version, field provenance, model ID, prompt version, source text version and token metadata. Failed reprocessing preserves prior successful candidates and financial records. Usage failures with unknown token counts retain null, rather than claiming zero consumption. Injected providers are explicitly marked offline tests, not verified free-tier activity.

## Offline corrections and matching

Open **Invoice Review**, sign in with a private local role key, select/upload a PDF, inspect its original and enter/correct evidence. The server records changed fields as human evidence with actor/reason and creates a new candidate; previous evidence remains immutable. Empty fields stay missing. Corrections work without cloud credentials. Original PDF access is authenticated and tenant-scoped; the historical demo invoices may have no retained PDF. The browser shows rasterized original pages from authenticated `/pages/{page}` reads and offers the unchanged PDF download. It never enables embedded PDF scripts. Rendering uses the same resource/network restrictions as extraction, at most 20 pages, 1600-pixel output, a 25-second deadline and two concurrent previews per API process.

Choose `two_way_exact_v1` or `three_way_exact_v1`. Matching resolves one exact active supplier and a PO reference/ID; line identifiers take priority, followed by a unique exact case-insensitive description. There is no fuzzy matching or currency conversion. The engine verifies line and header arithmetic, supplier, PO, currency, tax mode, unit prices, quantities, proportional header discount/tax, received quantities and supplier invoice duplicates. Partial invoicing allocates header discount/tax proportionally with Decimal and explicit HALF_UP rounding. Exact policies tolerate zero minor-unit difference. Overflow produces manual review.

Completed runs retain immutable candidate and PO/receipt/reservation snapshots, discrepancy codes and an audit event. Outcomes are `matched`, `unmatched`, `discrepancy`, `duplicate`, `needs_review`, and `extraction_failed`; the existing invoice status projection remains backward compatible. A terminal first structured extraction failure has a failed run/evidence classification; it is never a successful reconciliation. Legacy non-structured reconciliation/supplier processors retain their explicit unsupported result.

Human acceptance requires the latest candidate, current invoice version, a completed matched result, and an unchanged PO/receipt/capacity snapshot under locks. Receipt changes invalidate stale review. Acceptance publishes a separate human-confirmed financial version through the existing accounting validator; only such publications reserve ordered/received quantities for other invoices. Historical synthetic arithmetic fixtures do not consume new workflow capacity. Rejection records a human decision without approving anything. Published supplier/currency/PO bindings require a separate corrective invoice if those bindings need to change. Payments remain prohibited.

## Parser and OCR restrictions

Production local workers use a disposable parser process with a clean environment, 10 MiB input, bounded output, 25-second wall deadline, 20-second CPU allowance, 768 MiB address-space limit, 24 MiB file limit, 64 descriptors and disabled core dumps. The Python parser retains its stream/decompression/work limits and rejects encrypted PDFs. Linux seccomp denies socket/network creation and connections in the parser and OCR descendants. Compose Python services use a read-only root filesystem, temporary filesystem, non-root UID, dropped capabilities and no-new-privileges.

Tesseract English plus Poppler are installed in the Linux image. OCR is disabled by default; set `RECONCILE_OCR_ENABLED=true` and recreate workers to enable it for textless PDFs. Digital PDFs avoid OCR. OCR is capped at three pages, 1800-pixel rendering, eight-second command deadlines, and confidence/word-count screening. Low-confidence/blank pages fail to manual review. Mixed digital/scanned PDFs currently retain blank page text rather than selectively OCR those pages; review is required for missing fields. Host macOS lacks Tesseract/Poppler; use the verified Linux runtime. Unsupported Linux architectures fail closed on sandbox setup.

This is **not a complete hostile-document isolation boundary**. The child can read the container's non-root filesystem and same-UID process metadata; the application and parser share a container/kernel. Resource limits, seccomp and clean environment reduce exposure but do not establish production parser security. OCR confidence is an engine signal, not field-level verification. No OCR accuracy or hostile-document resistance claim follows from the single scanned smoke fixture.
